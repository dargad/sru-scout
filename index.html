Blocked SI-5055 LP 2168803 (qemu) Backlog · Alex Ramírez

LP: #2168803 · qemu · QEMU 8.2.2 guests crash by exhausting vm.max_map_count with coroutines

Issues

  • The backported patches parse /proc/sys/vm/max_map_count incorrectly, so the default value is always used and the system limit is never honoured. The upstream fix is not yet merged, and the SRU would ship known-broken code unless the correction is included.
  • The default value returned by get_global_pool_hard_max_size is UINT_MAX, which makes the hard cap ineffective. The conservative fix (65530) is only submitted upstream, not merged, and must be included in the SRU.
  • The fix reads /proc/sys/vm/max_map_count, so libvirt's AppArmor profile must allow it. The libvirt change (LP #2170732) is still pending, and qemu would need a versioned Breaks on libvirt to force the upgrade. Without both, the new code may be denied access to the file or misbehave under confinement.
  • The fix only reduces the likelihood of hitting the limit and does not eliminate it. A QEMU guest still crashes with 'failed to set up stack guard page' at the noble limit (1048576) with 255 vCPUs. The Impact section and the test plan must state this residual risk clearly.
  • The analysis is incomplete. Live-migration threads' contribution to cached coroutines is unexplored. The reproducer and the Impact text have changed repeatedly, so regression and verification coverage may be insufficient.
  • Development release is not fixed yet
