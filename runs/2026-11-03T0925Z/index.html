Blocked SI-4583 LP 2155998 (os-prober) BLOCKED · Bhavya Dokuru

LP: #2155998 · os-prober · Handle invalid grub config entries due to os-prober defaulting unidentified file system types

Issues

  • The reviewer wants the problem understood and reproduced from the boot side before accepting the patch. The test plan only shows a duplicate snapshot entry, not that the entry is invalid or unbootable.
  • The 'Where problems could occur' section is wrong. It says os-prober is disabled by default, but it is enabled automatically when other OSes are detected at install time. The regression potential must be re-assessed and rewritten.
  • No analysis of what the fuseblk fallback path does for real filesystems that grub-probe doesn't recognise, such as NTFS or exFAT. Removing it could stop os-prober detecting legitimate other OSes, so the regression risk is unquantified.
  • The original hanging-mount bug was reportedly fixed separately with mount namespaces. The rationale for reverting the fuseblk default needs to be reconciled with that, and the claim that the fix 'does not cause any side effects' is unsupported.
  • The bug text says the issue is invalid grub entries, but the reproduction shows a duplicate and redundant entry. The Impact and Test plan don't establish that it is harmful. The test plan also lacks explicit verification steps showing the entry is gone after the fix, and the bug is not a regression proven on Noble/Jammy.
  • The Other info section says the latest os-prober should be backported to Noble and Jammy after this SRU. The affected series, and the target releases for this fix, are not clearly defined or sequenced.
  • Development release is not fixed yet

Blocked SI-5055 LP 2168803 (qemu) Backlog · Alex Ramírez

LP: #2168803 · qemu · QEMU 8.2.2 guests crash by exhausting vm.max_map_count with coroutines

Issues

  • The backported patches parse /proc/sys/vm/max_map_count incorrectly, so the default value is always used and the system limit is never taken into account. The fix is still pending upstream and is not yet in the SRU.
  • The default hard max returned by get_global_pool_hard_max_size is UINT_MAX, which effectively disables the cap. The proposed fix is a conservative 65530 default, and it is not yet merged upstream or in the SRU.
  • Reading /proc/sys/vm/max_map_count needs a libvirt AppArmor change, which is tracked in a separate bug (LP 2170732). Without it the new code may be denied access. A versioned Breaks in qemu is probably needed to force the libvirt upgrade, and it is not confirmed as done.
  • The fix only reduces the risk of exhausting max_map_count. At very large vCPU or thread counts QEMU can still crash, and the crash was reproduced under the noble limit with 255 vCPUs. The remaining behavior at the limit has not been fully answered.
  • The upstream patches fixing the parsing and the default value have not been merged to qemu master. They may lack review, and the SRU would carry unmerged downstream patches.
  • The reviewer questioned whether the SRU is needed at all, since noble's kernel already has a much higher default limit and the crash was seen mainly on a 5.15 kernel with a 65530 limit. The justification, especially given the live-migration contribution not being explored, may need strengthening.
