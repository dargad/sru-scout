Blocked LP#2168803 QEMU 8.2.2 guests crash by exhausting vm.max_map_count with coroutines

LP: #2168803 · qemu · QEMU 8.2.2 guests crash by exhausting vm.max_map_count with coroutines

Issues

  • The backported patches parse /proc/sys/vm/max_map_count incorrectly, so the default value is always used and the system-limit awareness the fix relies on does not work. The corrected upstream patch is not yet merged, and it is unclear whether it is included in the SRU.
  • The default returned by get_global_pool_hard_max_size is UINT_MAX, which effectively removes the cap. A conservative default such as 65530 is needed. Combined with the parsing bug, the shipped fix would not enforce any hard limit. This second fix is also unmerged upstream.
  • The patch reads /proc/sys/vm/max_map_count, which needs a libvirt AppArmor rule. Without that rule, confined guests cannot read the file. A versioned Breaks/Depends in qemu is also needed so libvirt is upgraded together with qemu. Neither is confirmed done; the libvirt fix is in a separate bug (2170732).
  • The fix only reduces the chance of hitting the VMA limit. With very many vCPUs or threads, QEMU can still crash (reproduced at 255 vCPUs with the noble limit of 1048576). The SRU must be described as mitigation, not a full fix.
  • The post-fix reproducer still crashes with 255 vCPUs under the noble limit, and a peak of 509362 VMAs was seen with the overcommitted test plan. The test plan and Impact section changed repeatedly, so verification may be unclear and the impact on real noble users is debatable, because noble's higher default limit already avoids the crash in most cases.
  • The upstream follow-up patches (the parsing fix and the lower default max pool size) were submitted but not yet merged. The upstream status and the reason for the delay are unanswered, and the SRU diverges from upstream until they land.
